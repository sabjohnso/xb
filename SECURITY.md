# Security Policy

## Reporting a vulnerability

Please report security issues privately via **[GitHub Security
Advisories](https://github.com/sabjohnso/xb/security/advisories/new)**.
GHSA gives us a confidential channel to coordinate a fix and a release
before any public disclosure.

Please do **not** open a public issue or PR for a security report.

You can expect:

- Acknowledgement within 5 business days.
- A first triage assessment within 10 business days.
- A target remediation date communicated as part of triage.

If you have not heard back within those windows, escalate by mentioning
`@sabjohnso` on the advisory thread.

## What is xb?

xb is a C++20 library and CLI for parsing XML Schema (XSD), RELAX NG,
DTD, Schematron, WSDL, and SOAP, plus a Binary Encoding Specification
(BES) compiler that emits zero-copy C++ types for binary protocols.

The threat model differs by how you use it. Two distinct surfaces:

### Build-time use (CLI / codegen tool)

`xb generate`, `xb fetch`, `xb sample-doc`, `xb convert`, `xb generate-xsd`,
`xb-bootstrap`, and the CMake integration scripts run **on the
operator's machine**, consuming schemas the operator chose. The
inputs are operator-trusted: an XSD with a hostile annotation could
inject text into generated headers, and a hostile `<xs:import
schemaLocation=...>` could (without our defenses) reach attacker-
controlled URLs.

We harden this surface anyway, on the assumption that schemas are
sometimes downloaded from third parties or generated by upstream
tooling that can itself be compromised. See the threat boundaries
below.

### Runtime use (linked library `xb::library`)

A service that links `xb::library` to parse SOAP envelopes, validate
XML against a schema, decode a BES wire frame, etc., processes
**attacker-controlled bytes** on every request. Defenses here are
mandatory; the library's hardened defaults exist for this case.

## Trust boundaries

| Input source | Trust level | What xb assumes |
|--------------|-------------|-----------------|
| Schemas (XSD, RNG, DTD, Schematron) loaded by the CLI | **Operator-controlled** | The operator chose this file. Hostile annotations are still mitigated (comment-block injection is escaped; codegen output paths refuse symlinks; clang-format invocation never reaches a shell), but xb does not treat the schema as adversarial input by default. |
| URLs in `xs:import schemaLocation`, `xs:include`, RNG `externalRef`, WSDL `wsdl:import` | **Schema-author-controlled (= attacker-influenced)** | Refused unless the scheme is on `fetch_options::scheme_allowlist` (default `{"https"}`). Bare local paths require explicit `allow_local_paths = true`. |
| HTTP destinations resolved by `http_transport` / `mtom_transport` | **Schema-author-controlled (= attacker-influenced)** | Refused if the resolved IP is in loopback / RFC 1918 / link-local / cloud-metadata ranges, unless `block_private_destinations = false`. The check re-runs after each redirect via `CURLOPT_PREREQFUNCTION`. |
| HTTP responses from those destinations | **Attacker-controlled** | Bounded by `max_response_bytes` (default 64 MiB), `max_redirects` (default 5), `CURLOPT_REDIR_PROTOCOLS_STR=https`, `CURLOPT_SSL_VERIFYPEER`, and an explicit `CURLOPT_SSL_VERIFYHOST=2`. |
| XML parsed by `expat_reader` (any document) | **Attacker-controlled** | External entity references refused (`XXE`); parameter entities not parsed; foreign DTD disabled; billion-laughs amplification capped at 100x with a 1 MiB activation threshold. Opt-in `allow_external_entities = true` for legitimate use of trusted external entities. |
| Numeric strings parsed into `xb::integer`, `xb::decimal`, `xb::duration` | **Attacker-controlled** | Capped at 4096 decimal digits (`xb::max_decimal_digits`); arithmetic checked for `int64_t` overflow; `int32_t` storage range checked before narrowing. |
| HTTP request bodies received by `http_listener` | **Attacker-controlled** | `bind_address` defaults to loopback; `max_request_bytes` defaults to 16 MiB (413 on excess); `Transfer-Encoding` requests refused (501); malformed `Content-Length` produces a 400. |
| BES-encoded wire frames | **Attacker-controlled** | `extract_bits` / `insert_bits` abort cleanly on undersized buffers rather than reading past. Generated `_view` constructors validate `wire_size <= buf.size()` for fixed-layout messages when `validation_level >= structural`. The `from_trusted` factory bypasses validation by design — only invoke it when the caller has independently validated the buffer. |
| WS-Security UsernameToken digests | **Attacker-controlled** | `wss::verify_username_token` recomputes the digest with `SHA-256` by default (SHA-1 opt-in for OASIS UsernameToken Profile 1.0 interop), constant-time compares, and bounds `Created` against a 1-minute skew window by default. |
| WS-Security `wsu:Timestamp` | **Attacker-controlled** | `wss::validate_timestamp` rejects `Expires` in the past and `Created` more than the skew window in the future. |
| WS-Addressing `ReplyTo` / `FaultTo` / `From` | **Attacker-controlled** | `extract_addressing_headers(env, opts)` rejects addresses outside `endpoint_validation_options::address_allowlist` (the WSA `anonymous` URI is always permitted). |
| Codegen output paths | **Operator-controlled, but shared FS may be hostile** | All codegen output sites use `O_NOFOLLOW`; pre-existing symlinks at the target path are refused. |
| `clang-format` invocation by `code_formatter` | **Operator-controlled** | Invoked via `posix_spawnp` with an explicit argv array — schema-derived filenames cannot reach a shell. |

## Patterns where xb's defenses *do not* apply

These are documented gaps, not bugs. Future work is tracked in
`PLAN.org`.

### XML signature verification (Phase 3b — deferred)

xb has no implementation of XMLDsig (Exclusive C14N, RSA chain
validation, strict reference resolution against XML signature
wrapping). Services that require a signed SOAP envelope to be
cryptographically verified must do that verification themselves
(or use a different library) until Phase 3b lands.

`wss_codegen` therefore does **not** emit `verify_signature(...)`
calls in generated client stubs. The only WS-Security verification
xb provides today is UsernameToken digest + Timestamp / Created
window — see `xb::wss::verify_username_token` and
`xb::wss::validate_timestamp`.

### Pattern-engine choice

xb defaults to **RE2** for pattern matching wherever the engine
choice is xb's to make.  RE2 guarantees linear-time matching and is
not vulnerable to catastrophic backtracking even on hostile patterns
or inputs.  A host without RE2 does not silently lose that guarantee:
the configure step takes RE2 from `find_package(re2 CONFIG)` or
pkg-config when either finds it, and otherwise builds RE2 and Abseil
from the revisions pinned in `cmake/xb_deps.cmake`.  Selecting
`std::regex` instead is an explicit decision, made by configuring with
`-Dxb_USE_RE2=OFF`.  A build that must not reach the network can set
`-Dxb_FETCH_RE2=OFF`, which turns the source fallback into a configure
error rather than a silent downgrade.

- `src/lib/naming.cpp` — applies regex rewrite rules from the
  naming-config file using `re2::RE2::GlobalReplace` when xb is
  built with RE2.  Falls back to `std::regex_replace` when RE2 is
  not available.

A second call site in `src/lib/codegen.cpp` emits regex calls into
*generated* code, which then runs at the consumer's runtime.  By
default xb still emits `std::regex_match` there for backwards
compatibility — that path's threat model is the consumer's, not
xb's, and changing it forces a downstream link dependency on RE2.
A future major version bump will flip the default.  Today, an
operator who wants RE2-based validation in generated code can opt
in via the `--validation-engine=re2` flag to `xb generate` (see
`PLAN.org` Step 5b.3).

### Plaintext password mode in `wss::username_token`

`password_text_type` is supported but no longer the default
(`password_digest_type` with SHA-256 is the default). Plaintext
passwords have no value over a TLS connection that already protects
the channel, and xb provides no constant-time helper for verifying
them — the receiver compares them itself. If your policy forbids
plaintext entirely, refuse `password_type == password_text_type` at
your handler boundary.

## Dependency policy

Third-party CMake dependencies (`Catch2`, `nlohmann_json_schema_validator`,
`json-commander`, `CTestDeps`) are pinned to released tags or specific
commit hashes in `cmake/xb_deps.cmake`. The pins are revisited:

- **Immediately**, on a CVE published against the pinned version
  (we rely on GitHub Dependabot security alerts for the watch).
- **Quarterly**, on a scheduled review pass (Q1 / Q2 / Q3 / Q4) to
  catch upstream drift before it becomes urgent.
- **Need-driven**, when a specific upstream fix is required by xb.

Build-only dependencies (`Catch2`, `json-schema-validator`,
`json-commander`, `CTestDeps`) have a lower urgency than would-be
runtime dependencies, since their compromise affects xb's developer
machines and CI rather than xb's runtime users. `expat`, `libcurl`, and
`OpenSSL` are consumed via system packages, which carry their own
upstream security policy. `RE2` and the `Abseil` it requires are the
one runtime pair CMake will fetch, and only when the host provides
neither: that build links code from the pinned revisions rather than
from a distribution that patches and advertises its own advisories, so
it carries the same urgency as any other pinned runtime dependency.
Configuring with `-Dxb_FETCH_RE2=OFF` turns the source
build into a configure error instead.

The pins are **enforced** via `CACHE STRING ... FORCE` so a stale
build cache cannot silently downgrade them. Intentional override (e.g.
to test an unreleased Catch2) requires editing
`cmake/xb_deps.cmake` directly.

## Build hardening defaults

The `multi` preset (and its derivatives `ci`, plus the per-compiler
user presets) builds Release with:

- `-D_FORTIFY_SOURCE=3` — fortified C-library boundary checks.
- `-D_GLIBCXX_ASSERTIONS` — libstdc++ precondition checks
  (catches `vec[i]` past size, dangling iterators, etc.).
- `-fstack-protector-strong` — stack-smashing protection.
- `-fstack-clash-protection` — stack-clash mitigation.
- `-Wl,-z,relro -Wl,-z,now` — full RELRO with immediate binding.
- `-Wl,-z,noexecstack` — non-executable stack.

`RelWithDebInfo` adds `-fsanitize=undefined,address` and keeps
`-D_GLIBCXX_ASSERTIONS` for development-time bug catching.

These flags apply to **xb's own compilation** via the preset. They do
**not** propagate to downstream consumers via the exported
`xb::library` target — a downstream project linking xb selects its
own Release flags via its own preset/toolchain. xb's build choice
intentionally does not leak across the API boundary.

## Fuzzing

libFuzzer harnesses for the major parsers ship under `test/fuzz/`.
They build only when `-Dxb_BUILD_FUZZERS=ON` and the compiler is
Clang, and are intended to be run manually rather than in CI.  Each
links `-fsanitize=fuzzer,address,undefined` so coverage-driven inputs
are exercised under ASan + UBSan simultaneously.

| Target | Parser exercised |
|---|---|
| `xb_expat_reader_fuzz` | `xb::expat_reader` (XML, with the Phase 1 hardening) |
| `xb_dtd_parser_fuzz` | `xb::dtd_parser` |
| `xb_rng_compact_parser_fuzz` | `xb::rng_compact_parser` (RELAX NG Compact) |
| `xb_rng_parser_fuzz` | `xb::rng_xml_parser` (RELAX NG XML form) |
| `xb_schema_parser_fuzz` | `xb::schema_parser` (XSD 1.1) |
| `xb_mime_multipart_fuzz` | `xb::mime::parse_multipart` plus the `xb::xop::from_multipart` / `xb::xop::deoptimize` cid-resolution path |
| `xb_bes_choice_fuzz` | `xb::wire::*_view` dispatch over the `choice` test schema. Exercises both the validating constructor and `from_trusted` against the Phase 2.4 `wire/bits.hpp` bounds-check, in both fixed-layout and variable-layout (discriminated) shapes. Inputs are padded to ≥ 16 bytes so the fuzzer drives accessor logic rather than re-discovering the documented `require_buffer_size` abort. |

Seed corpora live under `test/fuzz/corpus/<harness>/`; see the
README in that directory for suggested seeds drawn from the
integration test fixtures.

To run a fuzz session:

```sh
cmake --preset clang-20 -Dxb_BUILD_FUZZERS=ON
cmake --build build-clang-20 --config Release \
      --target xb_<parser>_fuzz
build-clang-20/test/fuzz/Release/xb_<parser>_fuzz \
    test/fuzz/corpus/<parser> -max_total_time=300
```

Outstanding fuzz coverage tracked in `PLAN.org`:

- A BES (Binary Encoding Specification) dispatch harness — the
  binary-format parser xb generates from `xb::wire`.  Requires a
  committed BES test schema for the harness to dispatch into; not
  yet wired up.
- Differential fuzzing against `xmlsec1` once Phase 3b lands an
  XML-Signature verifier.

Findings should be reported via the GHSA process above, not as a
public PR / issue.
